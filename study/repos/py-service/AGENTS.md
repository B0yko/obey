# AGENTS.md

Working agreement for anyone changing ledgerline (people and coding agents alike).
ledgerline is a small invoicing and inventory library: Python 3.11+, standard library only at runtime, SQLite for storage.

## Layout

- `src/ledgerline/` holds the library; `tests/` mirrors it with one `test_<module>.py` per module.
- `migrations/` holds the numbered SQL migrations that `Database.migrate()` applies in order.
- `scripts/` holds maintenance scripts; `src/ledgerline/generated/` is produced by them.

## Tooling and dependencies

- Use `uv` for every Python package and environment operation (`uv run`, `uv sync`, `uv add`). Never call `pip`, `python -m pip`, `poetry` or `conda`.
- Do not add a new dependency, runtime or dev, without asking first. If a task seems to need a package, write the small stdlib version in `src/ledgerline/` or ask in your final message.
- Do not hand-edit the dependency tables in `pyproject.toml`; use `uv add` or `uv remove` when a change has been approved.

## Code

- Annotate every function signature and dataclass field. Code must pass `strict` mypy.
- Never use `Any` (`typing.Any` or `Any` in an annotation). Prefer `object`, a `Protocol`, a `TypedDict`, or narrow with `isinstance`.
- Do not write `# type: ignore` comments. Fix the types instead.
- Do not silence lint with `# noqa`; fix the code or ask before changing the ruff config.
- Never use `print(` in `src/`. Log through `logging.getLogger(__name__)` at module level.
- Pass log arguments lazily (`logger.info("sent %s", number)`), not through f-strings.
- Money is `Decimal` wrapped in `Money`. Never convert amounts with `float(...)`.
- Raise the exceptions from `errors.py` (`ValidationError`, `NotFoundError`, ...) and never a bare `Exception`.
- Keep functions short (about 40 lines at most) and prefer early returns over deep nesting.
- Public functions and classes get a one-line docstring in the imperative mood. Comments explain why, not what.
- Make small, focused changes. Do not reformat or reorder code you are not otherwise touching.

## Files and naming

- Every new `.py` file starts with `# SPDX-License-Identifier: Apache-2.0` on its first line.
- Python modules and test files use snake_case names, and tests are named `test_<module>.py` inside `tests/`.
- New migrations are named `NNNN_snake_case.sql` with the next free four-digit number.

## Database and generated code

- Never edit an existing file in `migrations/`, even to fix a typo or rename a column. Schema changes go in a new numbered migration (the next one is `0004_...`).
- A migration that changes a table also needs the matching change in `src/ledgerline/db.py`.
- Files in `src/ledgerline/generated/` are generated by `scripts/gen_currency.py`. Do not edit them by hand; change the script and run `make gen`.

## Testing

- Every change to code under `src/` comes with a test change under `tests/`.
- Run the test suite (`make test`) before you finish, and fix what fails.
- Run the linter (`make lint`) before you finish, and fix what it reports.
- Never skip or disable tests to get green: no `@pytest.mark.skip`, `xfail` or `pytest.skip(`.

## Git

- Write commit messages as Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`), with an imperative subject of 72 characters or fewer.
- Do not commit unless the task explicitly asks you to. Leave your changes in the working tree.
- Never run `git push`, and never force-push, under any circumstances.

## Reporting

- End your final message with a short summary: a line starting `Summary:` that says what changed and which checks you ran.
